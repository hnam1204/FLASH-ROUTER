# Threat model

AUTH-BROWSER-02 offline certification adds headed Chrome coverage only against a local mock origin with disposable SQLite/Vault data. The production origin allowlist remains official HTTPS only. The certification provides no evidence for live provider identity, CAPTCHA/SSO completion, cookie policy, or real-account session retention; those gates remain explicitly unverified.

Current assets are source code, local configuration, SQLite data, the DPAPI key ring, encrypted vault ciphertext, provider credentials, normalized provider observations, and transient user-authorized credential input. The primary controls are localhost-only binding, project-local runtime paths, redacted diagnostics, authenticated Data Protection encryption, passphrase-gated Authenticator sessions, provider/connection-scoped vault keys, fixed official HTTPS hosts, bounded response bodies, disabled redirects, cancellation/timeouts, rate-limit handling, explicit Check All confirmation, and synthetic-only security fixtures.

Provider failures are classified without converting missing permissions or unsupported reports into zero values. Check history stores normalized values and safe status/correlation metadata, never raw responses or authorization headers. The scheduler is disabled by default and scheduled checks exclude billable usage/cost capabilities unless explicitly changed in local configuration.

Remaining gates include official OAuth/provider authorization, portable cross-user recovery UX, live provider capability verification, package-vulnerability remediation, and production hardening. BE-02 has offline-tested local lock, DPAPI key protection, masking, and secret leakage boundaries. BE-06 adds encrypted SQLite backup payloads, vault ciphertext-only snapshots, SHA-256 integrity metadata, reparse/path traversal defenses, disposable restore validation, and active-database preservation. No live provider credentials, billable requests, or active user data were used.

The BE-06 package scan reached NuGet and reported transitive advisories for `System.Security.Cryptography.Pkcs 8.0.1` and `System.Security.Cryptography.Xml 8.0.4`; release hardening must update or otherwise disposition those dependencies before a security-clean release claim.

UI-E adds account-isolation controls around browser launch and secure copy. Profile directory references are validated against the managed local root before launch, account ownership is checked in SQLite, and launch failure is not promoted to an authenticated state. Credential copy requires Vault unlock and explicit confirmation; the default copy path is metadata-only. The browser integration never reads cookies, local storage, password-manager data, or session tokens.

The managed browser threat boundary also includes profile ownership races. A per-profile coordinator prevents simultaneous managed-Chrome and Playwright persistent contexts, canonicalizes Unicode-capable paths, distinguishes active lock metadata from stale metadata, and releases leases on early exit, cancellation, and disposal. `PROFILE_IN_USE`, permission, executable, timeout, navigation, and early-exit categories remain separate so a failed launch cannot be promoted to an authenticated state. No lock file is removed and no unrelated Chrome process is terminated.

Live acceptance remains a separate trust decision. `BrowserOpened`, `BrowserSessionObserved`, `StoredCredential`, `OAuthAuthorized`, and `VerifiedIdentity` are not interchangeable. Standard provider API keys do not imply management-level credits, balance, billing, or organization usage permissions.

The current local runtime smoke test applied the pending `AddBrowserProfileBindings` migration to the existing integrated database and then reported the database up to date on restart. No account rows, Vault files, backups, or key-ring files were reset or deleted. This local mutation is recorded for auditability and is not evidence of a disposable migration run.
